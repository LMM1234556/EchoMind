## 未通过场景

1. `greeting`：回答内容符合问候和能力介绍契约，但意图输出为 `request`，而固定标签为 `greeting`。
2. `multi_agent_payment_login`：回答同时覆盖 401 和重复扣款，但意图输出为 `technical_login`，只选择 Technical 主 Agent，未形成预期的 Billing 主 Agent + Technical 辅助 Agent 路由。
3. `multi_turn_refund_memory` 第 1 轮：退款意图和 Billing 路由正确，但“请记住订单号并正在申请退款”没有足够政策事实问题，Evidence Selector 拒绝候选；系统返回无证据模板，未满足该旧用例要求的回答词面。第 2 轮正确利用同一会话并回答到账时效。

前两项反映真实意图/复合路由不稳定；第三项同时暴露旧综合用例契约与当前严格证据门控之间的语义冲突。不能仅通过修改标签或放松门控把它们改成通过。

## 结论边界

- 本轮证明当前 Docker 链路可完整运行，并覆盖问候、政策有证据、技术故障、人工升级、复合请求、知识缺口和多轮会话。
- 62.50% 是 8 次固定请求的严格端到端契约通过率，不是线上总体准确率。
- 该小样本结果与 95 条意图冻结集、60 条检索集、24 条证据门控集衡量的是不同层级，不能互相替代或拼成一个“总准确率”。
- 当前代码收尾完成；若继续优化，应优先处理问候确定性识别、复合领域召回和“记忆指令”与政策证据门控的分流。继续优化后才需要新冻结集，当前复现完成不以 v3 测试集为前提。
