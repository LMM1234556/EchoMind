# 意图评测数据规范

## 1. 正式指标的数据基础

代码中的 Few-shot 模板、关键词 Pattern 和开发期回归用例用于系统调试与迭代。正式指标采用规则冻结后独立收集、人工复核且与模板隔离的测试样本，使评测结果具备清晰的数据来源和可复核性。

## 2. 标签状态

- `draft`：候选标签，用于整理与人工复核。
- `verified`：已完成人工文本、标签和歧义检查，并填写 `reviewer`，可纳入评测。
- `rejected`：经复核后移出当前评测范围，适用于语义不清、主次意图难以确定或超出当前标签体系的样本。

仓库中的 `backend/evaluation/data/intent_eval_candidates.json` 是首批人工复核的开发集种子，用于改进和回归检查。`backend/evaluation/data/intent_test_v1.json` 是优化前的冻结合成测试集；`backend/evaluation/data/intent_test_v2.json` 是模型优化完成后、在首次预测前于 2026-10-26 完成人审并冻结的第二套合成测试集。准确率由独立冻结测试集统一计算。

## 3. 标注原则

1. 优先选择细粒度意图。例如“退款多久到账”标为 `refund`，以区别于宽泛的 `billing`。
2. 通用意图用于处理缺少对应细粒度类别的消息。例如只说“账单看不懂”可标为 `billing`。
3. 一条消息包含多个并列诉求时，优先标记主诉求；主次难以确定的样本进入独立的多意图路由评测集。
4. 标签依据业务定义独立确定，并与当前模型预测保持隔离。
5. 测试集采用独立编写的文本，与 `_TEMPLATES`、关键词 Pattern 和开发期调试问题保持隔离。

### `escalation` 与 `human_handoff` 的边界

- `human_handoff`：用户明确要求人工、真人、人工坐席或真人客服。
- `escalation`：用户要求主管、负责人、经理或更高级别介入处理。
- `complaint`：用户表达不满，并由当前客服流程继续处理。

例如，“机器人解决不了，请接人工坐席”标为 `human_handoff`；“请把问题升级给主管处理”标为 `escalation`；“你们的处理结果让我很不满意”标为 `complaint`。

### `account` 与 `account_security` 的边界

- `account`：正常维护姓名、邮箱、绑定手机号等账户资料。
- `account_security`：存在账户被盗、异常登录、密码泄露、密码重置、两步验证等安全风险。

例如，“更换绑定手机号”标为 `account`；“陌生设备登录了我的账号”标为 `account_security`。标签依据用户诉求和风险事件确定，常规资料维护归入 `account`。

## 4. 建议规模与切分

数据集规模以类别覆盖、样本独立性和难例充分性为核心。约 500 条可作为当前 19 个意图的阶段目标，同时为容易混淆的类别配置更多样本。建议分阶段建设：

- 第一阶段：每类至少 10 条已复核样本，用于发现标签定义问题。
- 第二阶段：每类至少 20 条，并增加口语、错别字、省略表达和相邻类别难例。
- 第三阶段：达到约 500 条后冻结测试集；后续优化在训练集和开发集上进行。

推荐切分为 70% `train`、15% `dev`、15% `test`。正式报告使用与调参过程保持隔离的 `test`。

## 5. 独立测试集冻结流程

测试候选池以提交 `3aeca2011262594b1a6b8f774795909f3df9dbdf` 作为待测模型基线。该候选池共 95 条，覆盖 19 个意图，每类 5 条。冻结过程如下：

1. 项目负责人在模型预测前逐条复核文本与标签；有歧义的样本标为 `rejected`，进入单独的复核清单。
2. 分批复核期间，通过的记录更新为 `label_status: verified` 并填写 `reviewer`，同时保留 `split: candidate`，确保全量样本统一进入首次评分。
3. 全部完成人审后，将通过记录一次性更新为 `split: test`，记录文件 SHA-256，形成内容固定的 `intent-test-v1`。
4. 冻结后执行一次基线评测。评测发现的错误模式转化为新的开发样本，用于提示词、关键词、Few-shot 或阈值优化。
5. 后续改进使用新版本独立测试集验证；v1 作为内容固定的历史基线持续保留。

这 95 条文本由 AI 起草并经项目负责人人工复核，构成受控的合成测试集。简历或面试中将其表述为“人工复核的合成冻结集结果”；未来接入真实客服试点后，再增加线上流量指标。

## 6. 指标

- `Accuracy`：全部样本中预测正确的比例。
- `Macro-F1`：先分别计算每个意图的 F1，再平均，使各类别获得同等权重。
- 每类 Precision、Recall、F1：用于定位退款/账单、登录/账户安全等混淆。
- 混淆矩阵：查看错误主要流向哪个相邻类别。

随着样本规模增大，报告将同时提供点估计与置信区间，并保留模型、提示词、数据版本和运行日期。

## 7. 校验命令

在 `backend` 目录执行：

```powershell
python -m evaluation.intent_dataset evaluation/data/intent_eval_candidates.json
```

完成人审、将 `label_status` 更新为 `verified`、填写 `reviewer` 并分配到 `dev` 或 `test` 后，对应样本会计入输出中的 `scoreable_total`。

测试候选池还需同时与开发集比较，检查完全重复文本：

```powershell
python -m evaluation.intent_dataset evaluation/data/intent_test_v1.json `
  --compare evaluation/data/intent_eval_candidates.json
```

人审和冻结阶段将测试候选池的 `scoreable_total` 保持为 `0`，并在完成冻结后统一运行意图识别模型。冻结后的 v1 应显示 `frozen: true`、`scoreable_total: 95`；首次评测发现的问题进入开发集，原测试集持续作为内容固定的回归基线。
