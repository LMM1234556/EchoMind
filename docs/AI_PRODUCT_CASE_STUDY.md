# EchoMind：AI 产品案例

## 1. 案例摘要

EchoMind 是一个面向企业软件客服场景的 Multi-Agent AI 产品原型，致力于把复杂客服请求拆解成可路由、可验证、可引导核验和可复盘的产品链路。

本案例基于已有 EchoMind 项目进行产品化改进和工程验证。个人工作范围包括环境复现、Qwen API 接入、中文 Embedding 迁移、RAG 证据门控、多 Agent 路由修复、记忆隔离、故障降级和分层评测；不将原始系统描述为个人从零独立开发。

## 2. 用户与业务问题

### 目标用户

- 企业软件的一线客服：需要快速判断问题类型并给出下一步；
- 客服运营或知识库维护人员：需要知道回答使用了什么证据；
- AI 产品与研发团队：需要定位问题发生在识别、路由、检索还是生成阶段。

### 典型痛点

| 痛点 | 用户影响 | 产品风险 |
|---|---|---|
| 一条消息同时包含技术和账单诉求 | 只能解决其中一部分，用户需要重复描述 | 漏处理、重复转接 |
| 模型直接回答退款时效或费用 | 回复看似流畅，但可能没有平台依据 | 业务误导与信任损失 |
| 所有问题都检索知识库 | 闲聊也被无关文档干扰 | 延迟增加、误召回 |
| 只保存最终回复，不保存中间链路 | 无法解释为什么选了某个 Agent 或文档 | 难以迭代和回归 |
| 会话依赖外部存储 | Redis/ChromaDB 异常可能拖垮对话 | 可用性下降 |

## 3. 产品目标与当前范围

### 本阶段目标

1. 将产品咨询、技术故障、账单售后和人工升级分配给职责明确的 Agent；
2. 对平台业务事实建立“检索—选择—生成”证据链；
3. 证据充分时准确回答，证据不足时引导用户进一步核验；
4. 记录可用于评测和定位的结构化 Trace；
5. 在外部模型或记忆组件异常时提供清晰、连续的降级体验。

### 当前版本聚焦范围

- 使用演示知识库和模拟业务工具验证客服处理链路；
- 以固定开发/冻结样本建立准确率、延迟和回答质量基线；
- 使用 `MCPToolManager` 完成项目内工具治理；
- 使用项目负责人逐条事实复核作为当前回答质量依据；
- 以本地作品展示为当前交付形态，并为后续公网试点规划认证、限流和权限控制。

## 4. 产品方案

### 4.1 请求链路

```mermaid
flowchart LR
    U[用户请求] --> M[读取会话记忆]
    M --> I[意图与实体识别]
    I --> O[主/辅 Agent 路由]
    O --> K{是否需要业务事实}
    K -->|否| A[Agent 直接处理]
    K -->|是| R[BGE / ChromaDB 召回]
    R --> E[Top-3 Evidence Selector]
    E -->|证据充分| G[基于选中证据生成]
    E -->|证据不足| F[引导核验或转人工]
    A --> T[Trace 与监控]
    G --> T
    F --> T
    T --> W[写回会话记忆]
```

### 4.2 Agent 设计

| Agent | 主要职责 | 典型输入 | 响应原则 |
|---|---|---|---|
| General | 接待、澄清、一般咨询 | 问候、范围不明请求 | 平台业务规则以知识证据为依据 |
| Technical | 登录、错误码和排障 | 401、页面异常、配置问题 | 明确区分平台事实与通用技术建议 |
| Billing | 支付、退款、发票 | 重复扣款、退款时效 | 基于已确认的证据提供具体规则和时效 |
| Escalation | 人工交接与摘要 | 明确转人工、CRITICAL 请求 | 使用结构化信号触发，不解析自由文本关键词 |

Agent 按业务职责、工具和处理流程进行划分。复合请求由一个主 Agent 负责结果，辅助 Agent 提供跨领域支持。

### 4.3 RAG 证据门控

产品将两个问题明确分开：

1. **哪篇文档最相关？** 由关键词与 BGE 向量检索回答；
2. **这篇文档是否足以回答当前问题？** 由 Evidence Selector 回答。

Evidence Selector 最多读取 Top-3 候选的标题和正文，并与向量分数隔离，独立判断证据完整性。通过验证的一篇文档进入最终生成上下文；证据不足或服务异常时进入核验引导流程。

### 4.4 记忆与降级

- Redis：保存当前会话的工作记忆和 TTL；
- ChromaDB：保存可语义检索的历史摘要和用户画像；
- 达到压缩阈值后保留摘要与最近消息，避免上下文无限增长；
- Redis 异常时切换为无工作记忆模式，ChromaDB 异常时使用空长期记忆，保障本次回答连续可用。

## 5. 产品需求优先级

| 优先级 | 需求 | 判断依据 | 当前状态 |
|---|---|---|---|
| P0 | 高风险业务事实需完成证据确认 | 退款/费用规则需要可靠依据 | 已实现证据门控并评测 |
| P0 | 结构化执行明确的转人工请求 | 用户已表达渠道偏好 | 已使用结构化升级节点 |
| P0 | 用户与会话数据隔离 | 保障隐私与回答准确性 | 已验证 Redis/ChromaDB 隔离 |
| P1 | 复合技术+账单请求主辅协作 | 提升跨领域诉求覆盖率 | 机制已实现，并已识别复合领域召回优化方向 |
| P1 | 路由和证据可观察 | 支持排错和产品迭代 | 已在前端与 Trace 展示 |
| P2 | Skills 热加载 | 便于更新业务处理流程 | 已实现基础能力 |
| P2 | LLM-as-Judge 自动评分 | 提升评测效率 | 框架已实现，下一阶段进行人工一致性校准 |

## 6. 指标体系

系统按意图、检索、证据选择和完整链路进行分层评测，使每项指标对应明确的产品能力。

| 层级 | 关注问题 | 当前指标 |
|---|---|---|
| 意图 | 是否理解用户属于哪个业务场景 | 95 条、19 类冻结合成样本：Accuracy 98.95%，Macro-F1 98.94% |
| 检索 | 有答案时能否把正确文档排到前面 | 60 条冻结集：BGE Hit@1 97.22%、Hit@3 100% |
| 证据门控 | 能否识别知识缺口并选对已有证据 | 24 条冻结集：严格证据选择 87.50%，知识缺口正确识别 91.67% |
| 最终回答 | 回复是否忠于可用事实 | 24 条冻结集：项目负责人逐条确认的事实忠实度 83.33% |
| 综合链路 | 意图、路由、证据和回答是否同时满足契约 | 8 次真实请求：严格通过 5/8 |
| 工程回归 | 关键机制在版本迭代后是否持续稳定 | 151 项自动化测试全部通过 |

以上指标按各自样本范围独立解读。95 条意图集为项目负责人审核的合成冻结数据，24 条回答质量由项目负责人逐条进行事实复核，形成当前开发阶段的评测基线。

### 未来产品指标

进入真实业务试点后，指标体系将进一步补充人工转接率、一次解决率、证据覆盖率、用户重述率、平均处理时长、单次 token 成本和人工纠错率。

## 7. 关键迭代

### 迭代一：中文召回

发现原英文 MiniLM 对中文口语问法召回不足。通过同一冻结检索集比较后，迁移到 `BAAI/bge-small-zh-v1.5`；Hit@1 从 55.56% 提升到 97.22%。由于新旧模型维度不同，新建独立 ChromaDB collection 并保留回滚路径。

### 迭代二：从相关召回升级为证据确认

向量库会持续返回相关度最高的候选，因此产品进一步增加意图门控、领域过滤和 Top-3 Evidence Selector，在退款、发票等政策问题上完成证据确认后再生成回答。

### 迭代三：从成功截图转向冻结评测

将评测拆成意图、检索、证据门控和完整链路四层，保存原始 JSON 和 Markdown 报告。最终综合回归采用单次完整运行口径，定位出 3 个明确的产品优化方向。

### 迭代四：增强能力故障不阻断主链路

补充供应商超时、429、5xx、选择器非 JSON、工具熔断和 Redis 异常测试。Redis 异常时继续提供无记忆回答，外部模型异常返回明确状态并保留已有工具轨迹。

## 8. 当前评测发现与下一步

| 评测发现 | 产品解释 | 下一步 |
|---|---|---|
| 问候被识别为泛化 request | 简单高频意图不应完全依赖模型波动 | 增加高精度确定性前置规则 |
| “401 + 重复扣款”漏掉 Billing 路由 | 单标签意图可能覆盖复合诉求 | 增加复合领域多标签召回与路由测试 |
| “记住订单号”进入政策证据流程 | 保存信息和查询规则属于不同任务 | 在意图层分离 memory action 与 policy question |
| 回答可能扩展证据外细节 | 证据选择与最终表达需要协同约束 | 结构化事实输出与逐字段验证 |
| P95 响应约 68 秒 | 多次外部模型调用成为主要瓶颈 | 减少改写/重排调用，采集 token 与阶段成本 |

后续模型、Prompt 或阈值优化将使用新的独立冻结集验证，并保留当前结果作为可对照基线。

## 9. 作品集结论

本项目验证了将大模型客服拆解为一条具备清晰分工、证据确认、连续服务和评测反馈的产品链路，并基于真实评测发现确定下一轮优先级。

当前交付形态为本地作品集原型。下一阶段公网试点将补充认证、授权、限流、严格 CORS、日志脱敏、密钥托管、知识库审核和数据保留策略。
