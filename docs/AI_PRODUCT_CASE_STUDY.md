# EchoMind 产品案例

## 项目摘要

EchoMind 将产品咨询、技术故障、账单售后和人工交接组织成一条可观察的 AI 客服工作流。项目从场景定义出发，完成 Agent 职责设计、知识证据链、交互原型和分层评测，并根据评测结果迭代复合诉求覆盖与响应效率。

当前交付包括可运行系统、88 秒演示视频、需求与验收文档、评测数据和优化报告。维护者在原有架构上负责方案梳理、开发任务拆分、代码审阅、样本复核和结果分析，使用 Codex 辅助实现。[实现范围](IMPLEMENTATION_SCOPE.md)记录各模块的基础能力与改进内容。

## 1. 场景与需求输入

需求输入来自项目定义的客服场景、六份演示业务文档，以及后续冻结样本的实际回答。通过案例分析提炼处理流程；参与者行为观察另按[产品验证方案](PRODUCT_VALIDATION_PLAN.md)开展。

| 用户角色 | 需要解决的问题 | 产品响应 |
|---|---|---|
| 咨询用户 | 一条消息同时询问不同事项，希望获得完整回答 | 分项理解、分别取证、统一回复 |
| 一线客服 | 产品、技术、账单问题需要不同处理职责 | 四类 Agent 与明确的交接路径 |
| 知识维护人员 | 知道哪些规则有依据、哪些资料需要补充 | 显示证据来源和知识缺口 |
| 产品与研发人员 | 判断问题出在理解、检索、取证还是表达 | Trace、分层指标、失败分类与回归 |

例如，“登录 401 如何排查，100 积分能抵扣多少钱？”同时需要技术排障和积分规则；“密码忘了但手机号还在，电子发票最晚几天开好？”则同时包含有证据和资料缺口两个子问题。

## 2. 产品目标与优先级

| 优先级 | 需求 | 取舍依据 | 当前交付 |
|---|---|---|---|
| P0 | 平台事实有直接证据 | 退款时间、费用、积分比例影响用户决策 | 候选来源校验与 Evidence Selector |
| P0 | 明确的人工请求得到响应 | 交接路径应尊重用户选择 | Escalation 路由与交接摘要 |
| P0 | 会话信息准确归属 | 历史上下文影响本轮理解 | Redis 与 ChromaDB 标识过滤及隔离回归 |
| P1 | 覆盖复合诉求 | 漏答使用户重复表达 | 子问题拆分、并行选证、逐项回答 |
| P1 | 降低等待和调用消耗 | 多阶段模型调用拉长响应 | 组件级 Token 记录与思考策略 |
| P1 | 形成可复用验收方法 | 单次展示难以定位质量变化 | 冻结样本、人工量表、Judge 校准与回归 |

具体用户故事、功能要求、异常行为及验收规则见[需求与验收说明](PRODUCT_REQUIREMENTS.md)。

## 3. 方案设计

### Agent 按处理职责划分

| Agent | 处理职责 | 输出重点 |
|---|---|---|
| General | 接待、澄清、一般咨询 | 理解目标与下一步 |
| Technical | 登录、错误码、技术排障 | 平台依据、通用建议、验证方式 |
| Billing | 支付、退款、发票、账单 | 规则、金额、条件和处理时效 |
| Escalation | 人工服务与高优先级交接 | 用户目标、已知信息与待处理事项 |

编排器以结构化信息选择主辅 Agent，复合问题可采用跨职责协作；知识检索层同时按子问题确认各自的依据。

### 检索与证据确认分工

知识库先召回相关文档，Evidence Selector 再判断候选是否直接支持问题。选择结果要属于本次候选范围，并记录来源与证据状态。

复合请求中的各个子问题分别运行证据确认，生成阶段逐项回应。比如密码重置有账户安全文档支持，就提供重置指引；发票开具时限资料缺失，就说明需进一步核实，并提供人工路径。

### 记忆与运行反馈

Redis 保存近期对话与摘要；ChromaDB 保存历史摘要和用户画像。Skills 将客服流程与表达规则注入相应 Agent。调试工作台显示回答、意图、路由、证据和耗时，帮助维护者从具体案例追溯决策。

## 4. 评测如何形成迭代决策

### 中文检索：先建立可比较的对照

原 MiniLM 对中文口语查询的召回效果需要改善。项目在同一 60 条冻结查询上比较 MiniLM 与中文 BGE，排序指标统计其中 36 条有答案查询。

| 指标 | MiniLM | 中文 BGE |
|---|---:|---:|
| Hit@1 | 55.56%（20/36） | 97.22%（35/36） |
| Hit@3 | 83.33% | 100% |

采用中文 BGE 后，以独立 collection 管理新向量，保留旧 collection 便于回退。完整比较见[检索对照报告](../backend/evaluation/reports/retrieval_test_v1_first_run_20261026.md)。

### 回答覆盖：通过失败案例识别优先级

60 条首次目标回答按事实、诉求覆盖、操作真实性和安全要求进行验收：

| 结果 | 数量 |
|---|---:|
| 通过 | 27 |
| 部分完成 | 19 |
| 未通过 | 13 |
| 预算控制未完成 | 1 |

这轮评测发现复合诉求尤其容易只覆盖其中一项，因此将“子问题独立取证”列为下一次改进。调整后选取受影响的 048、049、051、052 四条原题开展定向回归，四条均经人工复核完成目标。[60 条基线](../backend/evaluation/reports/answer_coverage_60_v1_summary_20261106.md)与[后续配对记录](../backend/evaluation/reports/performance_ab_4cases_20261106.md)按版本保存。

### Token 与响应：按任务决定计算量

组件记录显示，意图识别、证据选择和画像提取只需短 JSON，却产生了较多思考 Token。优化方案是关闭这三类任务的思考模式，最终回复保留原配置。

对照固定为同一代码、Qwen 模型、知识库和四条问题。两组各使用全新的用户与会话，每组 19 次模型调用，包含后台画像提取。

| 指标 | 控制组 | 优化组 |
|---|---:|---:|
| 目标任务人工复核 | 4/4 通过 | 4/4 通过 |
| 总 Token | 36,817 | 22,099 |
| 平均响应 | 82.22 秒 | 34.77 秒 |
| 中位响应 | 77.37 秒 | 36.96 秒 |

在本批固定样本中，总 Token 减少 40.0%，平均响应减少 57.7%。两组按控制组、优化组顺序运行，延迟还受到供应商时段负载影响；后续扩展采用更多请求类型和交错顺序。详见[正式性能对照](../backend/evaluation/reports/performance_ab_4cases_20261106.md)。

### 自动评分：通过人工参考决定工具用途

项目完成 24 条回答的相关性、准确性、完整性和有用性四维评分，由两位评分者给出人工参考，并与 Judge 比较。16 条用于校准，8 条用于同批留出验证。

留出样本的平均 MAE 为 0.1789 → 0.1850，通过判断一致率保持 62.50%。因此采用决策为：人工复核承担质量验收，Judge 提供辅助评分和问题诊断。下一轮优先加强证据外数字、流程和承诺的识别，再验证评分规则。[校准分析](../backend/evaluation/reports/judge_calibration_v1_findings_20261104.md)保留完整结果。

## 6. 后续产品验证

下一步以 5–8 位参与者、每人五个固定任务开展形成性可用性测试，重点观察：

- 用户能否完成目标，在哪一步重复提问或需要帮助；
- 用户是否理解政策依据与知识缺口；
- 人工交接摘要是否足以继续处理；
- 等待时间是否影响任务完成；
- 根据任务完成率、用时、可信度与关键错误确定后续迭代。
