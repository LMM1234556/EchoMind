# RAG 检索层评测协议

## 1. 评测目标

本评测只回答一个问题：在相同知识库和相同查询上，中文 BGE 向量检索是否优于原 MiniLM 向量检索。

它不直接评估最终生成回答，也不把意图识别、Agent 路由或 LLM-as-Judge 的表现混入检索指标。因此，评测结果只能表述为“检索层指标”，不能表述为线上客服准确率或完整 RAG 回答准确率。

## 2. 固定比较对象

- 基线：`all-MiniLM-L6-v2`，384 维，独立 collection。
- 改进：`BAAI/bge-small-zh-v1.5`，512 维，独立 collection。
- 知识库：`backend/evaluation/data/retrieval_corpus_v1.json` 中的六篇文档。
- 两套方案必须使用相同文档内容、相同切片规则、相同查询和相同 Top-K。
- 不允许混用两个模型产生的向量，也不允许只为其中一套方案增加查询改写或 LLM 重排。

## 3. 数据分工

### 开发数据

`evaluation/retrieval_evaluator.py` 中既有的 seed、challenge 和 negative 用例已经参与过模型选择，只能用于：

- 检查评测程序；
- 分别校准两套模型的拒答阈值；
- 发现实现错误。

开发数据不得作为最终独立结果。

### 冻结测试数据

`backend/evaluation/data/retrieval_test_v1.json` 在冻结后包含 60 条人工审核用例：

- 36 条可由知识库回答的正例；
- 12 条业务相关但知识库缺少答案的难负例；
- 12 条超出业务范围的负例。

测试数据不得参与阈值选择、模型选择、Prompt 修改或检索规则调整。

## 4. 阈值校准

向量检索总能返回“最近”的文档，因此结果非空不等于存在证据。两套模型分别在开发数据上校准相似度阈值，固定规则如下：

1. 收集每条开发查询的 Top-1 相似度。
2. 把所有相邻观测值的中点以及区间两端作为候选阈值。
3. 正例只有在 Top-1 标题正确且分数不低于阈值时才算接受正确。
4. 负例在 Top-1 分数低于阈值时算正确拒答。
5. 选择使“可回答/不可回答”宏平均 F1 最高的阈值。
6. 若多个阈值并列，依次选择正确拒答率更高、阈值更高的方案。

阈值只能由开发数据产生，并须在首次测试运行前写入冻结清单。

## 5. 固定指标

### 正例排名指标

- `Hit@1`：期望文档位于第一名的正例比例。
- `Hit@3`：期望文档位于前三名的正例比例。
- `MRR@K`：期望文档排名倒数的平均值。

### 证据决策指标

- `Answerable Precision / Recall / F1`：系统决定“知识库可回答”时是否可靠。
- `Correct Rejection Rate`：24 条负例中被正确拒绝的比例。
- `Hard-negative Rejection Rate`：12 条业务难负例中被正确拒绝的比例。
- `Decision Accuracy`：60 条用例中，正例需标题正确且达到阈值，负例需低于阈值。

### 性能指标

- 平均延迟、P50、P95 和最大延迟。
- 模型首次加载属于预热，不计入查询延迟。

## 6. 冻结与首次运行

冻结清单必须记录：

- 测试集 SHA-256；
- 知识库 SHA-256；
- 评测代码所在 Git 提交；
- 两个模型名称与 collection；
- 两个开发集校准阈值；
- `first_evaluation_run=false`。

首次评测成功后写回报告路径、报告 SHA-256 和完成时间，并将 `first_evaluation_run` 改为 `true`。之后不得依据测试错例调整本次比较对象；若继续优化，需要新建开发数据和新的冻结测试集。

## 7. 结果表述边界

不得预设或追求“65% 提升至 83%”。最终只能报告实际测得的指标。即使 BGE 在本测试集上更高，也只能说明当前六篇演示文档和这 60 条人工审核查询上的受控结果，不能直接外推到生产知识库或真实客服流量。
