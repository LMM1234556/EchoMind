# RAG 检索层评测协议

## 1. 评测目标

本评测聚焦一个问题：在相同知识库和相同查询上，中文 BGE 与原 MiniLM 的向量检索表现有何差异。

评测对象明确限定为检索层，最终生成回答、意图识别、Agent 路由和 LLM-as-Judge 分别由对应评测集衡量。因此，本协议产出的结果统一表述为“检索层指标”，并与完整链路指标分开展示。

## 2. 固定比较对象

- 基线：`all-MiniLM-L6-v2`，384 维，独立 collection。
- 改进：`BAAI/bge-small-zh-v1.5`，512 维，独立 collection。
- 知识库：`backend/evaluation/data/retrieval_corpus_v1.json` 中的六篇文档。
- 两套方案使用相同文档内容、切片规则、查询和 Top-K。
- 两个模型分别生成并保存向量，查询改写和 LLM 重排配置保持一致。
- 评测器在本地生成文档与查询向量，并对两套模型统一使用余弦相似度；由独立计算流程消除 ChromaDB 服务版本和已有 collection 状态的影响。collection 名称用于记录两套模型在生产配置中的隔离关系。

## 3. 数据分工

### 开发数据

`evaluation/retrieval_evaluator.py` 中既有的 seed、challenge 和 negative 用例作为开发数据，用于：

- 检查评测程序；
- 分别校准两套模型的拒答阈值；
- 发现实现错误。

最终独立结果由冻结测试数据产生，开发数据用于校准和实现验证。

### 冻结测试数据

`backend/evaluation/data/retrieval_test_v1.json` 在冻结后包含 60 条人工审核用例：

- 36 条可由知识库回答的正例；
- 12 条业务相关但知识库缺少答案的难负例；
- 12 条超出业务范围的负例。

冻结测试数据与阈值选择、模型选择、Prompt 修改和检索规则调整保持隔离。

## 4. 阈值校准

向量检索总能返回“最近”的文档，因此结果非空不等于存在证据。两套模型分别在开发数据上校准相似度阈值，固定规则如下：

1. 收集每条开发查询的 Top-1 相似度。
2. 把所有相邻观测值的中点以及区间两端作为候选阈值。
3. 正例只有在 Top-1 标题正确且分数不低于阈值时才算接受正确。
4. 负例在 Top-1 分数低于阈值时算正确拒答。
5. 选择使“可回答/不可回答”宏平均 F1 最高的阈值。
6. 若多个阈值并列，依次选择正确拒答率更高、阈值更高的方案。

阈值由开发数据产生，并在首次测试运行前写入冻结清单。

## 5. 固定指标

### 正例排名指标

- `Hit@1`：期望文档位于第一名的正例比例。
- `Hit@3`：期望文档位于前三名的正例比例。
- `MRR@K`：期望文档排名倒数的平均值。

### 证据决策指标

- `Answerable Precision / Recall / F1`：系统决定“知识库可回答”时是否可靠。
- `Correct Rejection Rate`：24 条负例中被正确拒绝的比例。
- `Hard-negative Rejection Rate`：12 条业务难负例中被正确拒绝的比例。
- `Decision Accuracy`：60 条用例中，正例需标题正确且达到阈值，负例需低于阈值。

### 性能指标

- 平均延迟、P50、P95 和最大延迟。
- 模型首次加载属于预热，不计入查询延迟。

## 6. 冻结与首次运行

冻结清单必须记录：

- 测试集 SHA-256；
- 知识库 SHA-256；
- 评测代码所在 Git 提交；
- 两个模型名称与 collection；
- 两个开发集校准阈值；
- `first_evaluation_run=false`。

首次评测成功后写回报告路径、报告 SHA-256 和完成时间，并将 `first_evaluation_run` 改为 `true`。测试错例用于提炼新的开发样本；后续优化使用新的冻结测试集验证，本次比较对象作为固定基线保留。

## 7. 结果表述口径

最终报告采用实际测得的指标，并明确样本范围。BGE 结果代表当前六篇演示文档和 60 条人工审核查询上的受控表现；生产知识库或真实客服流量将在后续试点中独立评估。
