# EchoMind 小规模产品验证方案

## 验证目标

本轮产品验证回答三个问题：

1. 潜在用户能否完成退款查询、技术排障、知识缺口核验、人工交接和复合诉求处理；
2. 用户完成任务需要多长时间，在哪个步骤需要帮助；
3. 用户是否理解回答依据，并愿意信任系统给出的下一步建议。

这是一轮形成性可用性测试，目的是定位交互和产品链路问题。它衡量指定参与者完成指定任务的表现，与线上采用率、真实客服满意度分开报告。

## 参与者与测试方式

- 第一轮招募 5–8 位参与者；
- 优先选择使用过在线客服、SaaS 产品或智能助手的人；
- 每位参与者完成 5 个固定任务，任务顺序轮换；
- 主持人先说明“请边操作边说出想法”，任务进行中仅在参与者明确卡住时提供帮助；
- 记录匿名参与者编号，不收集姓名、联系方式或账户凭证；
- 每次测试预计 25–35 分钟，包括开场、任务和简短复盘。

## 固定任务

任务定义保存在 `backend/evaluation/data/product_validation_sessions_v1.json`。

| 场景 | 用户目标 | 主要观察点 |
|---|---|---|
| 退款政策查询 | 获得审核与到账时效 | 是否识别证据来源和下一步信息 |
| 401 登录故障 | 获得可执行排查步骤 | 是否理解 Agent 与工具 Trace |
| 知识缺口识别 | 询问未覆盖的发票时效 | 是否理解核验引导而非确定答案 |
| 人工交接 | 明确要求人工处理 | 是否确认结构化升级状态 |
| 技术与账单复合诉求 | 同时处理登录和重复扣款 | 是否覆盖两个领域且完成证据核验 |

## KPI 定义

### 核心指标

| 指标 | 计算方式 | 用途 |
|---|---|---|
| 严格任务完成率 | `success 任务数 / 已尝试任务数` | 衡量用户能否独立完成目标 |
| 成功任务用时中位数 | 成功任务 `time_seconds` 的中位数 | 衡量完成效率，降低极端值影响 |
| 平均可信度评分 | 所有有效 `trust_rating` 的平均值，1–5 分 | 衡量用户对回答和下一步建议的信任 |

### 诊断指标

- 部分完成率与失败率；
- P50/P95 任务用时；
- 证据清晰度评分与易用性评分；
- 需要主持人帮助的任务比例；
- 各场景任务完成率和用时中位数。

### 质量护栏

- **关键错误率**：出现编造政策、错误证据、遗漏明确人工请求或索取敏感凭证的任务比例；
- **超时率**：超过场景时间上限的任务比例。

关键错误直接进入 P0 修复清单。第一轮测试先建立基线，再根据场景差异制定下一轮目标，避免用缺少依据的统一百分比代替真实观察。

## 单个任务记录字段

每个任务完成后填写：

```json
{
  "scenario_id": "refund_policy",
  "outcome": "success",
  "time_seconds": 75,
  "trust_rating": 4,
  "evidence_clarity_rating": 4,
  "ease_rating": 3,
  "assistance_count": 0,
  "critical_error": false,
  "timed_out": false,
  "observation_notes": "能够找到 Trace，但先忽略了证据状态。"
}
```

`outcome` 使用 `success`、`partial`、`failed` 或 `not_attempted`。严格成功需满足该场景全部 `success_criteria`。

## 汇总命令

将匿名会话记录写入 `sessions` 后，在 `backend` 目录执行：

```powershell
python -m evaluation.product_validation `
  evaluation/data/product_validation_sessions_v1.json `
  --json-output evaluation/reports/product_validation_v1.json `
  --markdown-output evaluation/reports/product_validation_v1.md
```

当前模板的 `sessions` 为空，汇总状态会显示 `awaiting_sessions`。完成真实测试后，报告才会产生任务完成率、处理时间和可信度结果。

## 决策规则

1. 先处理所有关键错误，再比较完成率和处理时间；
2. 优先优化完成率最低或帮助率最高的场景；
3. 将参与者的行为观察与评分结合，评分仅用于解释行为结果；
4. 修复后使用相同任务结构和新参与者开展第二轮验证；
5. 对外展示时同时注明参与者数量、任务数量、测试环境和日期。
