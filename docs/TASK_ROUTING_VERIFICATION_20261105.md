# 订单信息任务分流与回归验证

验证日期：2026-11-05。

## 问题与结果

用户发送“请记住我的订单号是 EM-2026-1018，我正在申请退款”时，主要任务是提供信息。原链路按退款意图要求政策证据，容易返回缺少依据的提示。

当前通过[任务识别](../backend/core/task_routing.py)与[编排入口](../backend/agents/agent_orchestrator.py)分流完整匹配的显式订单号记录请求，确认收到用户提供的号码，继续沿用 `/chat` 的消息写入和后续历史读取。

示例确认语：

> 收到你提供的订单号：EM-2026-1018。请继续说明这笔订单需要处理的问题。

包含政策问句、业务操作、升级要求或其他未覆盖内容时，继续进入原 Agent 链路。CRITICAL、human_handoff 和 escalation 保持升级优先。路由原因和 Trace 会记录 `task=context_update`。

## 当前范围

- 识别明确的“记住／记下／记录／保存订单号”表达，支持一条用户提供的 4–32 位字母、数字、下划线或连字符订单号。
- 采用完整消息匹配，常见记录表达可附带“我正在申请退款／退货”的用户状态。
- 多订单、否定、敏感字段、政策问题、操作请求和不明确的附加内容留给原处理路径。
- 确认收到与存储写入分别处理；消息持久化沿用既有记忆组件，确认语不承诺永久保存或退款完成。
- 该分支跳过政策检索、证据选择和回复生成；HTTP 入口的意图识别与后台记忆维护保持现有流程。
