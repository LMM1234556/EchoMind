## 2. 本轮开发回归：订单信息补充

已知触发输入：

> 请记住我的订单号是 EM-2026-1018，我正在申请退款。

该请求提供订单信息，没有要求回答退款政策。新增[任务分流](../backend/core/task_routing.py)完整匹配明确的订单号记录请求，由编排器直接确认收到，API 继续沿用原有消息写入与后续历史读取。

[开发测试](../backend/tests/test_task_routing.py)共 35 项检查：

| 检查组 | 数量 | 验证目标 |
|---|---:|---|
| 显式订单信息补充 | 6 | 支持几种明确表达，保留用户提供的订单号 |
| 混合与不明确输入 | 20 | 政策问题、执行要求、升级、额外故障、否定、多订单、敏感字段和缺少订单号时进入原链路 |
| 编排与 Trace | 2 | 确认收到时跳过 Agent 生成／检索；在路由原因中标记 context_update |
| 升级优先 | 3 | CRITICAL、human_handoff 和 escalation 保持升级路径 |
| 政策取证 | 3 | 混合问句和后续政策问题继续检索，证据不足时保留核验引导 |
| HTTP 与记忆数据流 | 1 | 通过真实 `/chat` 路由，验证消息写入调用、后续 history 和再次取证；存储与模型采用测试替身 |

这些是根据已知失败与行为约束编写的开发检查，属于工程回归。原有意图、检索和回答冻结集继续按原内容保存，真实模型效果由后续受控运行检查。

当前确认语仅确认用户提供的信息。实际持久化由原有记忆组件执行；本轮不引入订单数据库或退款操作。HTTP 入口仍会进行意图识别及后台记忆维护。

## 3. 一轮集中补强的候选范围

以下 60 条问题、证据与预期行为已完成人工复核，接下来固定代码、模型和调用预算，安排一次正式回答验证：

| 场景组 | 候选数量 | 关注点 |
|---|---:|---|
| 单轮有证据 | 16 | 时间、条件、承诺程度与文档一致 |
| 知识缺口和近似主题 | 16 | 相关文档与充分证据的区别，给出合适的核验下一步 |
| 多轮任务与信息补充 | 12 | 记住信息、追问、代词、切换话题后的最终回复 |
| 复合诉求 | 8 | 技术和账单等诉求覆盖，主辅职责和分领域证据 |
| 人工交接与操作请求 | 8 | 确认人工偏好，生成交接信息，区分建议与已执行操作 |

数量单位为待评分的最终回答；多轮场景的前置请求另计。模拟 429、超时、Redis 不可用等故障检查独立保留为工程测试，不与真实模型回答质量混算。

意图数据优先在开发侧补充已知混淆；需要更强分类结论时，再按类别多样性安排扩充。约 500 条可作为参考规模，具体数量由用途和覆盖决定。

## 4. 执行顺序与固定条件

1. 修复已知问题并通过开发回归，记录代码版本。
2. 编写候选场景，逐条复核问题、证据、预期行为和歧义；开发用例与待验证问题分开管理。
3. 固定知识库快照、模型、提示词、通过标准和数据内容。
4. 根据前置轮数和各阶段调用估算请求数量，设定本轮调用上限、失败停止与续跑策略。
5. 集中执行一次，保留每条结果、失败及实际调用记录；出现基础设施故障时先记录和排查。
6. 人工复核回答与证据，按场景报告结果及后续决策。
