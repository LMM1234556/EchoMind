## 2. 60 条覆盖基线与改进闭环

| 场景 | 数量 | 验收重点 |
|---|---:|---|
| 单轮有证据 | 16 | 时间、条件、承诺程度与文档一致 |
| 知识缺口和近似主题 | 16 | 区分相关主题与充分依据，给出核实路径 |
| 多轮任务与信息补充 | 12 | 订单信息、追问、代词和话题切换 |
| 复合诉求 | 8 | 多个目标分别有证据并得到回应 |
| 人工交接与操作请求 | 8 | 交接信息、用户选择和操作状态 |

原始首次请求严格通过为 27/60（45%），用于定位固定覆盖场景中的改进机会。复合诉求组为 1/8，主要问题是单篇证据覆盖不足。由此实施子问题独立检索、并行选证和逐项回复，形成后续四条定向回归。

基线和定向结果按各自版本保留：60 条用于覆盖诊断，四条用于确认已知问题的改动效果。每条回答的事实、覆盖、操作真实性及安全性由人工复核。

## 3. 性能对照设计

两组固定为同一业务代码、同一模型别名、同一知识库和四条问题。控制组保持提供商默认思考配置，实验组对意图识别、证据选择和画像提取关闭思考；最终回复继续使用原配置。

每组运行前确认 Redis 会话键为 0，运行后每个会话均为两条消息。两组各 19 次模型调用，前台与后台 usage 完整，均为零自动重试、零换模、零 Judge。

- Token：36,817 → 22,099，减少 40.0%。
- 平均端到端耗时：82.22 → 34.77 秒，减少 57.7%。
- 人工验收：两组四条均完成目标。
- 解释范围：四个固定复合场景；运行顺序为控制组后实验组，延迟还受供应商时段负载影响。

[配对回答与逐次调用数据](../backend/evaluation/reports/performance_ab_4cases_20261106.json)支持结果复核。

## 4. 样本与版本管理

1. 在开发样本中定位问题并完成修改。
2. 审核测试问题、证据、预期行为和可能歧义。
3. 固定代码、知识快照、模型参数和评价规则。
4. 设置请求及 Token 预算，记录首次执行、异常和后续运行。
5. 独立复核回答，并按场景归纳问题。
6. 将改进映射到需求、代码与回归用例。

[意图数据规范](意图评测数据规范.md)和[RAG 评测协议](RAG评测协议.md)保留详细标注与冻结规则；[任务分流验证](TASK_ROUTING_VERIFICATION_20261105.md)记录早期 35 项订单信息补充检查。
